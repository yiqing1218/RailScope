# 联络线属性与类型编辑速度修复

当前快照 `769423dcd9e24eb78350498de462357a` 中，765 个现用名称包含“联络线”或“连络线”的目录对象，统一设置网络角色为 `connecting_line`，颜色为现有绿色 `#2e7d32`。原先保存的角色包括 400 个支线、227 个正线、81 个未知、3 个工业线和 54 个联络线。

本次通过工作区修改了 843 个属性记录，包含线路及相关单段覆盖；这不是 843 条独立线路。原始 OSM 标签、轨道角色、生命周期、几何、稳定 ID 和站场归属保留。名称分类保存了用户要求、快照、版本和来源证据；旧自动复查结果不会再次把名称中的联络线变回支线。

卡顿原因是选中单段修改 `rail_semantics` 后进入 `populate()`，以及普通线路撤销后重新生成目录。目录版本发生变化，又使站场目录缓存失效，触发“正在准备站场设施目录”。现在只修改铁路类别或线路功能时，增量保存对应属性、更新相关目录行、向地图发送对应对象的更新，并记下当前站场缓存版本。撤销和重做使用同样的局部更新。改变站场归属、轨道角色或运营状态仍走相应的结构与引用检查。

验证结果：

- 桌面测试全集：442 项通过；新增结构边界检查后，目录、联络线与对象编辑针对性测试 52 项通过。
- 全国实际数据批量保存：5.93 秒，过程中禁止调用全国目录或站场目录重建方法。
- 修改后再次检查：765 个目录对象全部为联络线，剩余需要修改的属性记录为 0。
- 实际地图的 10,527 个相关物理区段逐一验证，联络线属性及绿色均一致，失败数为 0。
- `rail.sqlite` 与 `rail_lines.sqlite` 的大小、修改时间不变；全部站场对象的 ID、父节点、类型、归属不变；再次准备站场目录直接命中缓存。

实际修改保存于 `data/user_settings/rail_catalog.workspace.sqlite`，样式保存于 `data/user_settings/rail_styles.json`。机器可读结果在 `data/user_settings/connecting-line-classification.json`。

可复用脚本：`python scripts/classify_connecting_lines.py` 默认预览，添加 `--apply` 应用到工作区。当前运行中的 RailScope 需要保存并重新打开，才能加载本次代码和样式。
